# v3 计划：示例体系、代码改动审阅、图导航、思考语义与使用指南

> 状态：**设计已确认，尚未实施**  
> 记录日期：2026-08-17  
> 本轮边界：只形成方案与验收标准，不修改代码、配置、工作流或运行账本。

v1 解决了“工作流是否能可靠运行”，v2 解决了“供应商、节点参数和运行过程是否可配置、可观察”。主人完成第二轮界面验收后指出五个产品完整性问题：

1. 正式工作流只有两个，不能体现 Atlas 可自由组合图结构的能力；
2. coding agent 的代码改动没有得到适合 Git patch 的专用展示；
3. 右下角 MiniMap 只显示当前视口，没有显示节点与图结构；
4. DeepSeek V4 Flash 显示“思考深度未配置”，语义不清；
5. 功能持续增加后，产品缺少完整、可导航的使用说明。

这五点不是同一种问题：第 2、3、4 项包含确定或高度可疑的实现缺陷，第 1、5 项是产品能力和信息架构尚未完整。本计划将它们作为一个连续阶段处理，但不把它们混成一次纯视觉改版。

---

## 0. 本阶段的结论与原则

### 0.1 五项结论

| 反馈 | 审查结论 | 性质 | 优先级 |
|---|---|---|---|
| 工作流只有两个 | 目录中确实只有两个里程碑样例，不是前端过滤；引擎能力远多于正式示例 | 产品缺口 | 高 |
| Diff 展示混乱 | patch 已产生，但独立产物没有完整进入 Web 数据链；现有组件又把 unified patch 当普通文本重算 | 确定缺陷 | **最高** |
| MiniMap 无节点 | 节点已传入，官方样式已加载；最可能是节点测量和 `fitView` 生命周期问题，需运行时确认 | 高概率缺陷 | 高 |
| DeepSeek 显示未配置 | 模型能力已探测且运行中产生 reasoning tokens；“未配置”只是 YAML 未指定档位，另有 API 漏传静态配置 | 语义错误 + 确定遗漏 | 高 |
| 缺少网站说明 | 当前只有观测台和设置，且没有正式路由；零散 tooltip 无法承载完整产品概念 | 产品缺口 | 中高 |

### 0.2 五条设计原则

1. **示例用于启发，不用于限制。** AI 可以在 Atlas 已验证的语法和安全边界内自由组合节点、分支、并行、汇合、多入口和有限循环。
2. **代码改动是一等产物。** patch 不是普通输出文本，不靠扩展名猜类型，也不对已生成的 patch 再做一次文本比较。
3. **能力、请求与响应分开表达。** “模型支持什么”“本次请求指定了什么”“本次实际观察到什么”是三个独立事实。
4. **缩略图必须表达结构。** MiniMap 不只是当前位置指示器，还要显示全图节点、相对布局和运行状态。
5. **说明是产品功能。** 使用者不应阅读源码或开发文档才能理解运行、思考、Diff、权限、成本和安全边界。

### 0.3 保持不变的红线

本阶段不改变 Atlas 已确立的四条红线：

- 不增加任意代码节点；
- 图定义仍以 YAML 文件为真相；
- 节点间数据不允许静默丢失，校验必须发生在花钱之前；
- Web 仍只监听 `127.0.0.1`。

“AI 可以自由设计任何结构”的准确含义是：

> AI 可在封闭节点类型、明确数据依赖、可校验路由和必然终止守卫内自由组合图结构；不代表可以绕开 schema、安全边界或运行守卫。

## 1. 当前事实基线

本节只记录已经从代码、配置、测试和运行账本确认的事实。未确认事项单独标注。

### 1.1 正式工作流与引擎表达力

`workflows/` 当前只有两个文件（M1 时期的事实快照；第五轮起为六个正式示例，
早期的 `sqlite-checkpoint-analysis` 与 `fix-calculator` 已删除）：

- `sqlite-checkpoint-analysis.yaml`：线性 `llm → llm → END`；
- `fix-calculator.yaml`：`coding_agent → reviewer → END`。

Web 和 MCP 都直接枚举工作流目录，不存在只显示前两个的筛选逻辑。只有两个选项是文件数量的真实反映。

现有 schema 和引擎已支持：

- `llm`、`research`、`coding_agent`、`human` 四种封闭节点类型；
- 单入口、入口列表和多根自动推断；
- 线性流程、并行扇出和多上游汇合；
- 结构化字段驱动的条件路由；
- 有条件出口且有 `max_iterations` 的有限循环；
- `task`、`<node>.output` 和 coding agent 的 `<node>.diff` 数据依赖；
- 多模型 fallback、重试、超时、输出上限、思考档位、权限与路径参数；
- 整图迭代、费用和墙钟守卫。

测试夹具已经覆盖并行、有限循环和人工审批，但它们没有被整理成可直接理解和运行的正式示例。

### 1.2 AI 设计工作流的现有闭环

当前入口是：自然语言 → skill 指导 harness agent 生成 YAML → MCP 校验和试运行 → 保存为文件 → MCP 运行。

已经具备：

- `atlas_validate_workflow`：可直接校验 YAML 文本；
- `atlas_run_workflow`：运行已经保存的工作流；
- `atlas_list_workflows`：列出工作流；
- `atlas_get_run`：读取运行状态。

当前边界：MCP 自身没有保存工作流的工具。完整闭环依赖 harness 同时拥有文件写入能力。这个边界不会阻止当前 ZCode/Claude Code 一类宿主工作，但会阻止“只会调用 MCP、没有文件工具”的 agent 完成创建。

### 1.3 coding agent 产物链

coding agent 会生成：

- 执行报告；
- Git patch；
- 对应哈希与事件记录。

真实运行已经证明 patch 可被下游 reviewer 消费，且原项目目录不被修改。但 Web 运行详情只稳定暴露普通输出路径，前端类型也没有把 `diff_path` 建模为独立产物。现有 Diff 分支因此正常情况下难以触达。

当前 Diff viewer 把 patch 作为相对空字符串的“新文本”做词级比较。这会破坏 unified diff 已有的文件、hunk、行号和增删语义。

### 1.4 MiniMap

已确认：

- React Flow 官方 CSS 已导入；
- 工作流节点和 END 已传给 React Flow；
- 自定义 CSS 没有显式隐藏 MiniMap 节点；
- xyflow 在节点尚无有效测量尺寸时不会绘制对应 MiniMap 节点，但仍会绘制 viewport mask。

因此“只看见当前视口框”高度符合节点测量尚未完成时 MiniMap 提前计算的表现。

尚未确认：运行时 DOM 中 MiniMap 节点究竟是不存在、尺寸为零，还是存在但颜色不可见。实施前需要一次浏览器 DOM 检查，不能把高概率判断当作最终根因。

### 1.5 DeepSeek V4 Flash 的思考状态

能力表已经把 `Deepseek:deepseek-v4-flash` 标为 `effort`。现有真实运行在未显式指定 `thinking` 时仍记录过 reasoning tokens。

两个正式示例没有写 `thinking`，所以事件中的 `thinking_tier` 为 `null`。它的真实含义是“Atlas 未指定档位，使用供应商默认行为”，而不是“模型不支持思考”或“本次没有思考”。

另有两个实现问题：

- 工作流详情 API 没有完整返回节点静态 `thinking` 配置；
- Anthropic 适配器当前用数值 `1` 表示“出现了 thinking block”，界面若显示为“1 思考 token”会造成错误理解。

### 1.6 网站结构

当前前端只有 `observe` 和 `settings` 两个内存视图，只在初始化时识别 `#settings`，没有完整路由。工作流、运行、节点和说明章节都没有稳定可分享的 URL。

## 2. M6-A：工作流示例体系与 AI 自由设计闭环

### 2.1 目标

让第一次打开 Atlas 的人既能看到一组经典、适用面广、可直接运行的工作流，又不会误以为 Atlas 只能运行这些固定模板；同时让只具备 MCP 能力的 AI 也能安全完成“设计—校验—保存—运行”。

### 2.2 示例、模板和自定义工作流的边界

产品中将工作流分为三种来源：

| 来源 | 含义 | 默认行为 |
|---|---|---|
| 示例 | 用于理解某种结构，模型待用户配置 | 仓库 LLM 模型留空；打开时列出待配置节点，不自动换模 |
| 模板 | 结构完整，但需要选择模型、路径或任务参数 | 打开时明确列出待配置项，不自动换模 |
| 自定义 | 由 AI 或用户根据具体目标生成 | 严格执行 YAML 的具体模型，不自动换模 |

示例和模板不是新的执行类型；引擎最终收到的仍是完全具体、通过同一套校验的 YAML spec。
`meta.kind` 不触发执行期自动选模。模型只来自 YAML 或显式 `node_overrides`；仍为空时
preview/dry_run 显示待配置节点，真钱运行在分配 run_id 前拒绝。有效规格写入 run 快照，
历史查看、恢复与审批不重新绑定。

### 2.3 首批正式示例

首批应控制在六个，覆盖最常用结构而不是追求数量。

#### 2.3.1 并行调研与综合 `parallel-research-synthesis`

**适用场景：** 技术调研、竞品分析、文献问题拆解。  
**结构：** 三个相互独立的 research/llm 节点并行 → synthesizer 汇合。  
**展示重点：** 多入口或扇出、汇合等待、完整原文消费、不同供应商。

#### 2.3.2 多模型辩论与裁决 `multi-vendor-debate-judge`

**适用场景：** 重要技术选型、方案风险判断。  
**结构：** 两到三个异质模型独立分析 → judge 保留共识、分歧与最终判断。  
**展示重点：** 独立上下文、异质模型、结构化裁决输出。

#### 2.3.3 方案审查与有限修复 `proposal-review-repair-loop`

**适用场景：** 方案草拟、文档修订、代码计划审查。  
**结构：** author → reviewer → 条件路由；通过则 END，需要修改则回 author。  
**展示重点：** 条件边、回边、退出条件、`max_iterations` 与 GuardViolation。

#### 2.3.4 人工审批管线 `human-approval-pipeline`

**适用场景：** 对外文案、敏感执行、关键决策。  
**结构：** draft → human → approved/finalize 或 rejected/revise。  
**展示重点：** 节点间暂停、批准/驳回、重启后恢复。

#### 2.3.5 代码实施与独立审查 `code-change-review-approve`

**适用场景：** 小型代码修复和可审阅变更。  
**结构：** coding_agent → 独立 reviewer → human。  
**展示重点：** 隔离副本、测试报告、typed patch artifact、Diff 专用视图和人工确认。

#### 2.3.6 长材料分片分析 `map-reduce-document-analysis`

**适用场景：** 长文档、多个实验记录或多份材料的联合分析。  
**结构：** 多个分析节点并行 → reducer 汇总。  
**展示重点：** 大输入、完整性哈希、长文本查看器和汇合。

`fallback-and-retry` 不单独占首批卡片，可作为上述示例中的故障演示模式或后续高级示例，避免让首屏变成机制目录。

### 2.4 示例元数据

当前顶层 schema 会拒绝未知字段。实现时应新增一个封闭的可选 `meta` 对象，而不是容忍任意未知字段：

```yaml
meta:
  title: 并行调研与综合
  description: 三个模型独立调研后由第四个模型综合
  kind: example
  category: research
  tags: [并行, 汇合, 多模型]
  estimated_calls: 4
  requires:
    workdir: false
    human_approval: false
  example_task: 比较三种本地工作流引擎的可靠性设计
```

约束：

- `kind` 只允许 `example | template | custom`；
- `category` 和 `tags` 只影响展示，不影响执行；
- `estimated_calls` 是静态提示，不冒充费用估算；有环时显示“每轮 N 次，上限 M 轮”；
- `requires` 只描述已能从 spec 推导或校验的要求；
- 所有字段有长度、字符集和数量上限；
- 未知元数据字段仍然拒绝，保持 fail-closed。

### 2.5 工作流发现界面

观测台左侧不再只显示一列文件名，而是提供：

- 推荐示例；
- 最近使用；
- 自定义工作流；
- 按“研究、决策、代码、审批、文档”筛选；
- 搜索标题、标签和描述。

每张工作流卡片显示：

- 中文标题和稳定 ID；
- 一句话用途；
- 节点数与结构标签；
- 预计调用次数或每轮调用次数；
- 是否需要工作目录或人工审批；
- 示例/模板/自定义来源。

选择工作流后仍进入同一个观测画布，不复制执行逻辑。

### 2.6 MCP 保存能力

新增受限工具 `atlas_save_workflow`，完成只调用 MCP 的 AI 创建闭环。

建议输入：

```text
workflow_id       必填，严格 ID 白名单
 yaml              必填，完整 YAML 文本
expected_sha256   更新已有文件时必填；新建时为空
```

处理顺序必须固定：

1. 对 ID 做白名单校验，拒绝路径分隔符、点路径和保留名；
2. 在内存中解析 YAML；
3. 执行完整 spec 校验、终止性校验和异质性提示；
4. 校验通过后生成规范化指纹；
5. 新建时拒绝覆盖已有文件；更新时使用 `expected_sha256` 做乐观并发控制；
6. 同目录临时文件 + 原子替换；
7. 返回工作流 ID、文件哈希、spec 指纹、警告和是否新建。

工具不得：

- 写出工作流根目录；
- 跳过校验保存“草稿”；
- 接受任意文件扩展名；
- 静默覆盖并发修改；
- 返回或嵌入任何密钥值。

是否删除工作流不属于本阶段必要闭环；在没有回收站和引用检查之前，不增加删除工具。

### 2.7 “自由设计”的产品表达

使用指南与工作流列表都要明确：

> 这些是起点，不是 Atlas 的结构上限。向接入 Atlas skill 的 AI 描述目标、约束和模型偏好，AI 会生成新的 YAML 图；Atlas 在保存或运行前验证结构、数据依赖和终止条件。

不得使用“任意工作流”这种没有边界的宣传，应说明四种节点类型和安全守卫。

### 2.8 验收标准

- 六个正式示例全部通过现有 A1–A11；
- 至少覆盖并行汇合、有限循环、人工审批和 coding agent 四种此前未在正式示例中完整体现的能力；
- 每个示例有用途、要求、调用次数和示例任务；
- 示例列表明确区分示例、模板、自定义，不让使用者误以为只能选固定模板；
- 仅使用 MCP 的 agent 能完成生成、校验、保存、运行；
- 任何不合法 YAML、越界 ID、并发覆盖或无出口循环都在写文件和花钱之前失败；
- 新保存的工作流刷新后可在 Web 和 `atlas_list_workflows` 中看见。

## 3. M6-B：代码改动作为一等产物与专用 Diff 工作区

### 3.1 目标

让使用者能够像审阅代码托管平台上的提交一样，准确看清 coding agent 改了哪些文件、哪些行、为什么改，以及 patch 是否完整；不再把 Git patch 当作普通 Markdown 或普通文本 Diff。

### 3.2 根因拆分

当前混乱来自三层，必须依次修复：

1. **采集层：** stat 摘要和 patch 可能混在同一文本中，递归缓存排除规则仍需验证；
2. **数据层：** 报告进入 Web 详情，但独立 `diff_path` 没有完整进入 API 和前端类型；
3. **展示层：** 已成形的 unified patch 又被相对空文本执行词级比较，语义被破坏。

只换 CSS 或换颜色不能解决这些问题。

### 3.3 统一产物模型

将节点产物从一组散落的 `*_path` 字段收敛为 typed artifacts。事件仍是唯一真相，API 从事件折叠得到列表。

建议结构：

```json
{
  "id": "implementer.diff.1",
  "name": "代码改动",
  "role": "diff",
  "media_type": "text/x-diff",
  "path": "artifacts/implementer.diff.1.patch",
  "sha256": "...",
  "bytes": 18420,
  "complete": true,
  "metadata": {
    "files": 3,
    "additions": 42,
    "deletions": 11,
    "binary_files": 0
  }
}
```

`role` 使用封闭枚举，首批至少包括：

- `report`：agent 执行报告；
- `output`：普通节点主输出；
- `diff`：Git patch；
- `projection`：节点完整输入投影；
- `raw`：需要保留但没有更具体语义的原始产物。

兼容策略：

- 旧事件继续可读；折叠器把旧的 `output_path/diff_path` 转成派生产物列表；
- 新事件写 `artifacts`，过渡期可同时保留旧字段；
- 前端只消费统一列表，不再根据 `.patch` 后缀推断含义；
- 每个产物继续保留哈希、字节数和完整性状态，不能为了 UI 重构牺牲 A1/A6。

### 3.4 Patch 采集规范

报告、stat 和 patch 分开：

- 报告：agent 的自然语言说明与测试结果；
- stat：机器解析的文件数、增删行摘要；
- patch：纯 unified diff，不在顶部混入 stat 文本。

采集要求：

- 递归排除任意深度的 `__pycache__/` 和 `*.pyc`；
- 默认排除明确的构建缓存和 Atlas 自身临时文件；
- 不默认排除用户源码或未知目录；
- 二进制文件记录状态，不把二进制字节塞入文本 patch；
- patch 超过上限时保存 stat 和截断原因，`complete=false`，绝不能把摘要伪装成完整 Diff；
- 新增、删除、重命名、权限变化和“文件末尾无换行”均原样保留 Git 语义。

长期可增加工作流级 excludes，但本阶段先采用封闭、保守的内建噪声清单，避免用户配置错误导致真实改动被隐藏。

### 3.5 Unified Diff 解析

前端不重新计算差异，而是解析已有 patch：

```text
Patch
└── File[]
    ├── oldPath / newPath
    ├── status: added | modified | deleted | renamed | binary
    └── Hunk[]
        ├── oldStart / oldLines
        ├── newStart / newLines
        └── Line[]
            ├── type: context | add | delete | meta
            ├── oldNumber
            ├── newNumber
            └── text
```

解析失败时：

- 不显示空白页面；
- 明确提示“结构化解析失败”；
- 保留原始 patch 查看和下载；
- 记录前端诊断信息但不篡改产物。

渲染安全：

- patch 内容始终作为文本节点渲染；
- 不允许原始 HTML；
- 语法高亮若加入，只对可见代码文本做 token 化，不使用未经净化的 `dangerouslySetInnerHTML`；
- 文件路径和 hunk 标题也按不可信文本处理。

### 3.6 专用 Diff 工作区

右侧节点详情继续承担摘要和快速查看，但“代码改动”打开全宽工作区。

#### 顶部摘要栏

显示：

- 改动文件数；
- `+N / -N`；
- 新增、删除、重命名、二进制文件数量；
- patch 完整/截断状态；
- 产物字节数与哈希验证状态；
- 原始 patch 下载。

#### 左侧文件树

- 按目录分组；
- 每个文件显示状态图标和 `+/-`；
- 文件名搜索；
- 当前文件高亮；
- 支持全部展开/折叠；
- 点击后滚动到对应文件并更新 URL 片段。

#### 主审阅区

- 默认 unified 视图；
- 可切换 split 视图；
- sticky 文件头；
- 固定旧/新行号栏；
- context/add/delete/meta 四种明确语义色；
- 代码默认不折行，横向滚动；可手动开启折行；
- 文件与 hunk 可折叠；
- 下一处/上一处改动导航；
- 复制文件 Patch、复制完整 Patch；
- 大 patch 只渲染可见文件和行。

#### 详情页签

coding agent 节点详情统一为：

1. 执行报告；
2. 代码改动；
3. 完整输入；
4. 失败记录；
5. 原始事件。

不存在对应产物时页签不伪造内容，而是显示“本节点未产生代码改动”等明确空状态。

### 3.7 视觉标准

- 增加和删除使用低饱和语义底色，文字仍满足 WCAG AA；
- 深色与浅色主题同时设计；
- 行号、代码和摘要数字使用 Geist Mono 与 `tabular-nums`；
- hover 只强化当前行，不用持续霓虹；
- 文件头和选中态沿用 Atlas 单一强调色；
- 键盘可完成文件切换、hunk 导航、视图切换和关闭工作区；
- `prefers-reduced-motion` 下取消滚动过渡和面板弹性动画。

### 3.8 验收矩阵

必须有夹具覆盖：

- 单文件修改；
- 多文件修改；
- 新建文件；
- 删除文件；
- 重命名；
- 二进制文件；
- 文件末尾无换行；
- 只有 stat、patch 被截断；
- 非法或无法解析的 patch；
- 大型 patch；
- 任意深度的 `__pycache__/*.pyc` 不进入 patch。

验收条件：

- API 返回 `diff` typed artifact，路径、哈希和字节数正确；
- 下游消费的 patch 与 Web 下载的 patch 字节级一致；
- 文件数和增删行摘要与 Git 结果一致；
- 不再出现“整份 patch 都被视为一篇新增文本”；
- 深浅主题、多文件、长行和大 patch 均可读；
- 解析失败时仍能访问原始真相。

## 4. M6-C：MiniMap 结构显示与画布生命周期

### 4.1 目标

MiniMap 必须同时回答两个问题：

1. 整张工作流是什么结构；
2. 当前主画布正在查看结构中的哪一块。

只显示 viewport mask 而没有节点，不满足缩略图的基本职责，按 Bug 处理。

### 4.2 实施前诊断

第一次改代码前，在浏览器检查：

- `.react-flow__minimap-node` 数量；
- 每个 SVG 节点的宽高是否为零；
- computed `fill`、`stroke` 和 `opacity`；
- MiniMap SVG 的 `viewBox`；
- React Flow 节点内部的 measured width/height；
- 首次加载、切换工作流和切换主题后的差异。

根据结果区分：

- **没有节点元素：** 优先修复初始化与测量时序；
- **节点尺寸为零：** 修复节点尺寸和布局契约；
- **元素存在但不可见：** 修复主题和对比度；
- **切换后才消失：** 修复组件复用和重新 `fitView` 生命周期。

### 4.3 目标实现

- 使用 `useNodesInitialized()` 或等价状态，节点测量完成前显示 MiniMap 骨架而不是残缺缩略图；
- 工作流 ID 变化后重新测量并调用 `fitView()`；
- 必要时以工作流 ID 作为图实例 key，避免沿用上一张图的 viewport；
- 将应用深浅主题显式传入 React Flow；
- MiniMap 显式配置背景、遮罩、节点填充、节点边框和遮罩边框，不依赖库默认变量；
- 节点颜色按 pending/running/done/failed/paused/degraded 映射；
- 当前选中节点有清晰边框，但不改变节点几何尺寸；
- END 节点使用独立但低干扰的形状或颜色；
- MiniMap 可平移主画布，但不承担节点编辑功能。

### 4.4 尺寸契约

Dagre 使用的节点宽高必须与 DOM 外框一致：

- 全局或节点局部采用 `box-sizing: border-box`；
- 节点宽高常量只有一个来源；
- 文本增加导致高度变化时，要么固定内容区域，要么将实测尺寸反馈给布局；
- MiniMap 使用 React Flow 的 measured dimensions，不另写一套估算。

### 4.5 验收标准

- 工作流加载后，MiniMap 节点数等于图节点数加 END；
- 每个节点尺寸非零；
- 相对布局与主画布一致；
- 当前 viewport 遮罩和节点都可见；
- 运行状态变化能在 MiniMap 中辨认；
- 切换两个结构不同的工作流后，不残留上一张图；
- 调整浏览器尺寸后重新适配；
- 深色、浅色和高对比场景均清晰；
- 组件测试覆盖初始化前、初始化后、工作流切换和主题切换。

## 5. M6-D：思考能力、请求档位与响应证据

### 5.1 目标

消除“未配置 = 不支持 = 没有思考”的误解，让使用者准确知道：模型能否接受控制、本次是否指定控制，以及供应商实际返回了什么证据。

### 5.2 三层语义

#### 第一层：模型能力 `capability`

表示 Atlas 对该模型控制接口的认识：

- `effort`：支持离散 reasoning effort；
- `budget`：支持 thinking token budget；
- `toggle`：只支持开关；
- `none`：已探测且不支持；
- `unprobed`：尚未探测。

能力不等于本次请求，也不等于本次一定产生思考内容。

#### 第二层：请求控制 `requested thinking`

- `provider_default`：YAML 未写 `thinking`，Atlas 不发送统一档位控制；
- `low`；
- `medium`；
- `high`；
- `xhigh`。

界面不再使用孤立的“未配置”，改为：

> 请求档位：供应商默认

#### 第三层：响应证据 `observed reasoning`

不同协议只能显示其真实可获得的信息：

- OpenAI 兼容响应返回精确 usage：`1,371 reasoning tokens`；
- Anthropic 只检测到 thinking block、没有精确用量：`检测到 thinking block`；
- 供应商未提供证据：`供应商未返回思考用量`；
- 指定了档位但没有观察到证据：显示 `档位可能未生效` 警告事件。

禁止把布尔 presence 值 `1` 显示为“1 token”。

### 5.3 数据模型

工作流详情 API 必须返回节点静态配置，至少包括：

```json
{
  "thinking": "high",
  "max_output_tokens": 20000,
  "temperature": null,
  "seed": null
}
```

运行节点摘要建议返回：

```json
{
  "thinking": {
    "requested_tier": "provider_default",
    "effective_kind": "effort",
    "effective_value": null,
    "evidence_kind": "reasoning_tokens",
    "evidence_value": 1371,
    "warning": null
  }
}
```

能力 API 返回的是模型能力记录，不返回密钥：

```json
{
  "model_ref": "Deepseek:deepseek-v4-flash",
  "kind": "effort",
  "protocol": "openai",
  "status": "probed",
  "probed_at": "...",
  "evidence": "reasoning_tokens",
  "effect_verified": false
}
```

`effect_verified=false` 很重要：当前探测能证明参数被接受并出现推理痕迹，但简单任务上 low/high 差异不足以证明档位强弱稳定生效。

### 5.4 界面表达

#### 画布节点

空间有限，只显示：

- 显式档位：`⚡ 高`；
- 供应商默认但观察到推理：`⚡ 默认`；
- 指定但可能无效：警告样式 `⚡ 高 ?`；
- 不支持或未探测不在节点标题堆字，通过 tooltip 说明。

#### 节点详情

单独分三行：

```text
模型能力    reasoning_effort · 已探测
请求档位    供应商默认
响应证据    1,371 reasoning tokens
```

如果效果尚未验证：

```text
控制效果    已确认接口可用；档位强弱尚未充分验证
```

#### 设置页

每个模型显示能力徽章：

- Effort；
- Budget；
- 开关；
- 不支持；
- 未探测。

拉取到模型列表只代表“模型可见”，不得自动显示为“思考能力已配置”。新增模型初始状态必须是 `unprobed`。

### 5.5 能力探测改进

探测脚本从“单次 high 调用”升级为可解释的探测：

1. 固定一个足够复杂但成本受控的任务；
2. 运行 baseline、low、high；
3. 每档至少保留响应证据和协议；
4. 区分“参数被拒绝、参数被接受但无证据、有推理证据、档位效果可区分”；
5. 记录网关、模型、协议、探测时间和样本数；
6. 写回能力表时合并旧记录，不因某个密钥缺失而整体覆盖丢失其他模型；
7. 探测失败不把旧的已确认能力静默降级为 `none`，而是记录最新失败状态。

这仍不是科学地证明模型内部“想得更深”，只能证明可观察接口行为。文案必须保持这个边界。

### 5.6 正式示例中的档位

示例不强制所有节点都显式指定档位：

- 需要展示成本/质量取舍的示例可显式配置；
- 其他示例保留 `provider_default`，展示它是合法、有意义的状态；
- 如果模板可能替换为不支持该档位的模型，应把 `thinking` 作为待配置项或不写，避免模板一换模型就在校验期失败。

### 5.7 验收标准

- YAML 写了档位时，工作流详情在运行前就能显示；
- 未写档位显示“供应商默认”，不再显示容易误解的“未配置”；
- DeepSeek V4 Flash 能同时显示 effort 能力、默认请求和实际 reasoning tokens；
- Anthropic presence 不显示为 token 数；
- 新拉取但未探测的模型显示 `unprobed`；
- 指定但无响应证据时 `effort_ineffective` 明确可见；
- 能力探测写回不会删除未参与本次探测的旧条目；
- A9/A10 继续通过，且 API/前端增加对应回归测试。

## 6. M6-E：正式路由与使用指南

### 6.1 目标

为 Atlas 建立一个产品内的、可分享链接的说明系统。它既解释“怎么用”，也解释“界面显示的事实意味着什么”，但不取代开发者架构和验证文档。

### 6.2 顶层信息架构

一级导航保持三项：

1. **观测台**：选择并运行工作流、查看图、节点和事件；
2. **使用指南**：概览、入门、概念、示例、安全和排障；
3. **设置**：供应商、模型、凭据状态和能力。

不增加大量一级入口，避免本地工具演变成门户式界面。

### 6.3 路由

短期采用 Hash Router，避免立即为 FastAPI 增加 History API fallback：

```text
#/observe
#/observe/workflows/:workflowId
#/runs/:runId
#/runs/:runId/nodes/:nodeId
#/runs/:runId/nodes/:nodeId/diff
#/guide/overview
#/guide/quickstart
#/guide/concepts
#/guide/examples
#/guide/models
#/guide/safety
#/guide/troubleshooting
#/settings
```

要求：

- 刷新后保持当前页面；
- 浏览器前进/后退与界面同步；
- 打开运行或节点 URL 能恢复对应选择；
- 无效工作流、运行或节点 ID 显示明确的本地 404 状态；
- route 参数仍使用现有 ID 白名单和 API 安全校验。

### 6.4 指南章节

#### 6.4.1 概览

- Atlas 是什么、适合什么、不适合什么；
- YAML、引擎、MCP、skill 和 Web 的关系；
- “文件是真相，事件是运行真相，Web 是观察入口”；
- 一张简化架构图。

#### 6.4.2 五分钟开始

- 启动 Web；
- 确认 MCP 和 skill；
- 选择示例或用自然语言要求 AI 设计；
- validate → dry-run → save → run；
- 在观测台查看节点输入输出；
- human 节点如何批准或驳回。

#### 6.4.3 工作流概念

- 四种节点；
- `prompt`、`consumes` 和 typed artifacts；
- 线性、并行、汇合、多入口、条件分支和有限循环；
- fallback 与 retry 的区别；
- 费用、迭代和墙钟守卫；
- 数据完整性与哈希。

#### 6.4.4 示例模板

每个示例包含：

- 适用场景；
- 小型结构图；
- 节点和模型角色；
- 预计调用次数；
- 所需配置；
- 示例任务；
- “在观测台打开”操作。

#### 6.4.5 模型与思考

- API 拉取模型与白名单选择的区别；
- capability、requested tier、response evidence 三层语义；
- 四档映射规则；
- `provider_default` 的含义；
- fallback 和真实异质性的限制。

#### 6.4.6 运行结果与代码改动

- pending/running/done/failed/paused/degraded/truncated；
- token、reasoning evidence、耗时和费用未知；
- 报告、输出、投影和 patch 的区别；
- 如何使用专用 Diff 工作区；
- 完整/截断产物如何识别。

#### 6.4.7 安全边界

必须突出：

- Web 只监听 `127.0.0.1`；
- 不支持任意代码节点；
- coding agent 使用目录副本，不是操作系统沙箱；
- 凭据值不会进入 API 响应，但同一 Windows 用户的本机进程仍是信任边界；
- 未配置费率时成本守卫不能凭空得出真实费用；
- 有环图仍受 `max_iterations` 和其他 guard 限制。

#### 6.4.8 排障与参考

- YAML 校验失败；
- 模型不可用或 fallback；
- 能力未探测；
- 输出截断或假成功；
- 运行等待人工审批；
- 崩溃后恢复；
- patch 解析失败；
- MiniMap 或事件流显示异常；
- 指向 README、ARCHITECTURE、VERIFICATION 和完整字段参考。

### 6.5 内容来源

用户指南内容采用受控 Markdown，而不是把长篇 JSX 写死在组件中：

```text
docs/guide/
  overview.md
  quickstart.md
  concepts.md
  examples.md
  models.md
  safety.md
  troubleshooting.md
```

构建时通过固定 manifest 导入允许的文件：

- 不接受 URL 或 query 参数指定任意本地路径；
- Markdown 继续禁用原始 HTML；
- 外部链接明确标识；
- 代码块、表格、提示框和内部章节链接有统一组件；
- 技术开发文档不全部暴露到产品导航，只链接必要内容。

这样用户指南和产品代码解耦，又不会创建读取任意本地文件的接口。

### 6.6 页面设计

- 左侧固定章节导航；
- 中间正文限制合理阅读宽度；
- 右侧按当前章节显示页内目录（窄屏隐藏）；
- 顶部提供全文搜索或至少章节标题搜索；
- 关键安全提示使用固定语义组件；
- 示例结构图复用只读 GraphView 缩略模式，不维护第二套图形语义；
- “在观测台打开”跳转到稳定 route；
- 继承现有深浅主题、Geist 排版和 reduced-motion 设置。

### 6.7 验收标准

- 三个一级入口清晰，指南不是临时弹窗；
- 每个指南章节有稳定 URL，可刷新、前进、后退和直接访问；
- 五项本阶段新增语义都能在指南中查到；
- 安全边界不埋在 About 页面末尾；
- 指南中的示例链接能打开对应观测图；
- Markdown 不执行原始 HTML 或脚本；
- 桌面宽屏和较窄窗口都可阅读；
- 对完全不了解技术栈的使用者，能只依靠指南完成“选示例—运行—看输出—理解思考状态—审阅 Diff”。

## 10. 本阶段明确不做

| 不做 | 原因 |
|---|---|
| 增加任意代码节点 | 违反安全红线 |
| 把示例固化为唯一可选结构 | 与 AI 自由设计目标相反 |
| 用模型重新总结或重写 patch 再展示 | 会丢失代码改动的字面真相 |
| 用“1 token”替代 thinking block presence | 语义错误 |
| 未诊断 MiniMap 就只调颜色 | 可能掩盖初始化根因 |
| 将全部开发文档直接暴露为网站页面 | 信息层级不合适，也扩大任意文件读取风险 |
| 删除工作流 MCP | 没有回收站和引用检查前属于不必要的破坏能力 |
| 宣称 low/high 一定改变模型内部思考深度 | 当前证据不足 |

## 11. 风险与降级策略

| 风险 | 应对 |
|---|---|
| 大 patch 造成前端卡顿 | 文件/行虚拟化，解析放到 worker 或分片；超过上限明确降级为摘要 + 原文下载 |
| Diff 语法高亮引入 XSS | 先安全文本渲染；高亮只用 token 树，不接收原始 HTML |
| 旧运行没有 typed artifacts | 折叠时兼容旧字段，建立旧账本回归夹具 |
| 示例模型待配置 | `kind: example` 不触发自动选模；preview/dry_run 列出待配置节点，真钱运行在 run_id 前拒绝 |
| Guide 与实现漂移 | 每个关键字段和状态来自共享常量或生成清单；发布前执行文档链接和字段校验 |
| MiniMap 库行为变化 | 对可观察 DOM 和节点数量写组件测试，不依赖人工截图 |
| 能力表被一次失败探测覆盖 | 合并写回、保留旧证据、记录最新失败而非静默删除 |
| MCP 保存覆盖人工修改 | `expected_sha256` 乐观锁 + 原子替换 |
